# Theme System Rules

## Architecture
- `THEMES` object (features.js, ~line 7850): each entry = `{name,bg,body,orbs[5],swatch,scenic?}`. `applyTheme(key,skipSave)` sets `--bg` custom property, `body.style.background` (light mode only), `.orb` inline backgrounds, toggles `.scenic-theme`/`theme-{scenic}` classes, and (since the Modern theme) `body.theme-modern`. Swatch picker (`#themePicker`) renders one `.theme-swatch` div per `THEMES` entry in object-insertion order — reordering the object reorders the picker, no separate list to maintain.
- `initTheme()` reads `localStorage._dashTheme` (default `'peach'`) and calls `applyTheme(key,true)` on load.
- **Dark mode is a SEPARATE toggle** (`body.dark`, see `rules/dark-mode.md`) that layers on top of whichever THEMES swatch is selected — `applyTheme()` only sets `body.style.background` `if(!cfg.dark)`, so dark mode's own background always wins when active regardless of swatch.

## Modern Theme (`body.theme-modern`, added 2026-09-21)
Opt-in Apple-Reminders/Mail-style theme, ported from the mobile app's own redesign (mobile.css). First in the `THEMES` list, replaced the old `frost` swatch. All its CSS lives in a clearly-marked block at the end of styles.css (search `body.theme-modern`).

**What it changes** (scoped to `body.theme-modern` unless noted "GLOBAL" below):
- `.card-hero` (the Today+Time-Block panel specifically, index.html — NOT other task-list cards) goes flat/transparent, no border/shadow — Today list sits directly on the page background. `border-radius` is left at the base 7px (do NOT zero it — a zeroed radius made important/overdue/selected row backgrounds look sharp-cornered and out of place; 7px matches what Weekly Reset/Shopping rows already use, so nothing needs to change on their end to match).
- `.ti-band`: a left-edge two-tone color bar replacing the round `.cat-dot` category indicator, Today-list only. Emitted by **every** Today-list row-render function that used to show a dot — `tRow`, `tRowTodayVirt`, `tRowShopVirt`, `tRowFinCancel`, `tRowVidVirt`, `tRowVidStepVirt`, `tRowPupSess` (all overview.js) — miss one and that row type silently keeps showing no color at all, not the old dot (the dot-hiding CSS is scoped to `#todList .cat-dot`, which already covers every function regardless of which one renders the row). `display:none` outside this theme (base rule at the top of the Modern section) so it's fully inert everywhere else. Notes-glow (see tasks-ui.md → Notes indicator) is applied as an inline `box-shadow` directly on the band's own style string in `tRow()` only — the other row functions never had a notes-glow feature to port.
- `.chk`/`.chk-wrap`: ring softened + fill made fully opaque, checked-state now translucent (`rgba(139,139,150,.4)` light / `rgba(190,190,198,.3)` dark) rather than solid — matches the base app's own faded-checkbox pattern instead of introducing a new solid-disc look. `clip-path:circle(50%)` added defensively (see Gotchas below). **Size enlargement (16px, was 12px) is `#todList`-only** — `body.theme-modern .chk{...}` alone would also inflate Weekly Reset/Shopping/Monthly-view/Kanban checkboxes, which all share the same `.chk` class; the color/ring changes stay unscoped (harmless everywhere) but width/height/z-index must stay under `#todList`.
- `.delbtn` (✕ delete button): SVG icon + explicit `width:16px;height:16px;padding:0` — **GLOBAL, all themes**, not just Modern (moved out on request: "standardize the sizing... not just within this theme"). `#recList .delbtn,#shopOv .delbtn{width:12px;height:12px}` gives the compact mini-cards a smaller icon.
- Quick Links (`.ql-btn`/`.ql-icon`/`.ql-pic`): neutralized from a hardcoded peach tint to flat neutral, then restyled as iOS-widget-style tiles — 15px "squircle" rounding, real soft elevation shadow (no color tint), bigger icons via `.ql-icon svg{width:19px;height:19px}` (the SVGs carry inline `width/height="18"` in index.html — CSS has to target the `svg` directly, `.ql-icon`'s own `font-size` does nothing to them), `.ql-pic{width:20px;height:20px!important}` for the Pups profile-photo `<img>` icons (needs `!important`, same inline-attribute reason).
- Notes/other minor: `.wr-unassigned` sizing tuned (see wr-system.md) — GLOBAL, not theme-scoped, despite being discovered during Modern-theme work.

**`.row1-right-top` grid ratio (GLOBAL, not theme-scoped)** — see `rules/pages.md` → Overview "Layout" for current values; tuned across several rounds this session (Weekly Reset wider at Shopping's expense, then Quick Links narrower/Shopping wider again to square its tiles) — **always measure the actual rendered px via `getBoundingClientRect()` before adjusting further, don't guess a second time off a stale screenshot** (this bit us once: a first correction overshot because it was computed from an old, pre-edit screenshot's pixel values instead of a live measurement at the actual current CSS).

## Gotchas (hard-won, don't re-litigate)
- **`.tn` needs a FIXED px `line-height`, not a ratio, not the CSS-default `normal`** (styles.css, base rule — GLOBAL, not theme-scoped, the bug isn't theme-specific): descenders (g/y/p) were clipping against `overflow:hidden` on selected AND unselected Today-list rows. `line-height:normal` is deliberately engine-dependent per the CSS spec (computed from the font's own internal ascent/descent metrics) — WebKit's calculation for this font was tighter than Chrome's, so the bug was never reproducible in this session's Chrome-based sandbox testing. A ratio (`1.3`) still wasn't reliably enough (still partly at the mercy of the font/engine's own em-box split) — settled on a fixed `17px` (12px font +5px), which removes the remaining engine-dependence entirely. If a similar "can't reproduce in Chrome, user reports clipping/visual glitch" bug comes up again, suspect a `line-height:normal`/ratio-based sizing property before anything else — see the checkbox and `:has()` entries below for two MORE instances of the exact same "Chrome ≠ this app's real WebKit" pattern in one session.
- **This app runs inside a native macOS WKWebView (DockClock), not a regular browser** — `window.webkit.messageHandlers.themeColor.postMessage(...)` (index.html's inline bootstrap script + `_updateThemeColorMeta()` in features.js) bridges the selected theme's color to DockClock's native title bar. Its bundled WebKit version is NOT guaranteed to support recent CSS features. **A `:has()`-based fix for `.ov-topbar`'s positioning (see core.md → Page Layout) silently no-op'd in the user's real session** — produced byte-for-byte identical (broken) numbers before and after deploying, the tell-tale sign of an unsupported selector rather than a logic bug. Re-implemented in plain JS (`.style.left=...` set directly by the functions that actually change sidebar state) instead. **Avoid `:has()` or other very-recent CSS selectors for anything load-bearing in this app — prefer plain JS DOM/inline-style manipulation.** `calc()`/`clamp()` as CSS *values* (not selectors) are confirmed working (pre-existing `#page-overview` padding already used `clamp()` successfully).
- **A "confirmed fix" that keeps failing for the user despite passing sandbox tests may mean the sandbox test is compensating for the same bug it's meant to catch.** This session's `.ov-topbar` sandbox testing repeatedly manually re-added `html.init-sb` before measuring — which is precisely the condition that's FALSE in the user's real session (that class is a one-time anti-FOUC bootstrap flag, removed by `openSB()`/`closeSB()` the instant real startup logic runs, see core.md → Sidebar). Don't manually restore `init-sb`/`init-dark` when testing steady-state layout in this sandbox's login-bypass pattern (`#loginOverlay` hidden directly rather than real auth) — leave it absent, matching real usage.
- **A hairline `border` on an absolutely-positioned decorative element can render visibly THICKER in one CSS multi-column (`columns:N`) column than another** — subpixel/anti-aliasing inconsistency between the two columns' fractional device-pixel offsets, not a color/opacity issue. `.wr-unassigned` hit this (see wr-system.md) — the real fix was abandoning `position:absolute` sizing-off-parent-height in favor of a normal in-flow flex child with a FIXED px height, which can't inherit the inconsistency since it's the same fixed value everywhere.
- **`.ql-grid{grid-template-columns:1fr 1fr}`'s two columns are not always pixel-equal even at 1fr/1fr** — a longer button label (e.g. "Birthdays"/"Finance") can force its column wider than a shorter one ("Videos"/"Pups") since grid items default to `min-width:auto` (≈min-content). Not fixed (a few px of variance across 6 tiles was deemed close enough to "square-like") — if pixel-perfect equal columns are ever wanted, add `min-width:0` to `.ql-btn`.
