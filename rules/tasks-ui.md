# Tasks & UI Rules

## Task Types on Overview

All task types that appear on the overview calendar/today list. Every type must support: render, select (`selTask`), drag, drop onto calendar day, multi-select drag with mixed types, timeblock drop, checkbox toggle, delete (X), undo.

- **Progress %**: Today list header shows completion percentage. Excludes `_type==='travel'` and `_type==='holiday'` items entirely (denominator too — neither has a completion mechanism, so counting them would permanently cap the % below 100). Excludes `_type==='birthday'` from the done count only (still in the denominator; done via linked TB block).

### Multi-select global behavior
- **Cmd/Ctrl+click**: toggle item in selection.
- **Shift+click**: range-select within same container.
- **Drag any selected item**: moves ALL selected items to target day, regardless of type.
- `_moveOtherSelected(ds, excludeSid, undos, excludePrefixes?)` helper handles cross-type multi-select for all drag handlers.
- Every drag handler must: (1) move its own type, (2) call `_moveOtherSelected` or inline-iterate `selectedTasks` for other types, (3) collect undo fns for all moved items.

## Overdue Logic
- **Tasks**: `due_date < today && !done && category !== 'Weekly Goals'`. Weekly Goals excluded from today overdue count/banner but shown as overdue (OV style) in WO modal and weekly cal goals column when viewing past weeks (`isPast` / `_goalsPast`). Carried-over overdue goals also appear on current week in weekly cal goals column, WO modal, and monthly view.
- **Weekly Goals overdue carry-over**: uncompleted goals from past weeks (`due_date < wkStart`) shown with OV style on current week. Each view has a stacked banner: "X Overdue" text + red "Move to this week" button. Clicking moves all overdue goals' `due_date` to current `wkStart`. Undoable. Banner appears in: weekly cal goals column, WO modal (with light red bg), monthly view goals cell (compact).
- **Shopping**: `due_date < today && !done`.
- **Non-WR recurring**: `getRecurringWeekTasks(w)` for w=0 to wkOff-4. Cascading `__skip__` check. Seen set prevents duplicates.
- **WR recurring** (`is_weekly_reset=true`): overdue if `_dateOverrides[wkKey] < today && !_doneByWk[wkKey]`. 4-week lookback. `wrRecHandled` set — only added when `_dateOverrides[wkKey] <= today` (future dates don't block older-week lookback).
- **WR rules** (`st.wrRules`): overdue if `_dateOverrides[wkKey] < today && !isDoneWRRule`. Same 4-week lookback + `wrRuleHandled` set with same future-date exception.
- **Pup sessions**: `day_date < today && !done`. Included in `updateOvBanner` count and `rolloverOverdue` (moves `day_date` to today, PATCHes `pup_skill_sessions`). Appear in today list when `dayOff===0`. Sorted by timeblock position (`_pupSessId` matched against `b._pupSessId` in `tbSm()`).
- **Videos**: overdue if `_vidDayMap[id] < today && status !== 'published'`. Included in banner count and rollover (moves localStorage date to today). Appear in today list with red `OV` style + day letter.
- Tasks/shopping/non-WR recurring only overdue if assigned to a date.
- **Non-WR recurring dedup**: `allRecVirt` deduplicates by `_recId::_wkKey`. Same task from different weeks = separate instances (e.g. HEB moved cross-week + this week's natural occurrence). Same task+week = deduped, preferring future over overdue. `getOvRecurring()` uses same `_recId::_wkKey` dedup for overdue banner/rollover.
- `updateOvBanner()` called from `renderToday()`. Banner text: `X Overdue` + `Move to today` button (`rolloverOverdue(event)`). Non-recurring types + same-week recurring/WR items (a task/WR-pin overdue from earlier *this* week — no schedule question) move silently, single combined undo. A genuine past-week recurring/WR miss instead gets its own sequential popup via `_rolloverPromptQueue` (features.js) — `showWrScopePicker` is a singleton so these fire one at a time, each choice triggering the next; every past-week miss gets prompted even when several are overdue at once. WR week-misses route through `wrMoveToThisWeek` for proper move-override bookkeeping.
- **Per-row "move to today" arrow** (`_dlblOvArrow`, overview.js): every overdue Today-list row (`tRow`, `tRowTodayVirt`, `tRowShopVirt`, `tRowVidVirt`, `tRowPupSess` — NOT vidsteps, which intentionally never auto-move) gets a small → after its day letter, shifted to `right:24px` (vs. the base `right:9px`) so it clears the always-visible (not hover-only — see `.ti.ov-row .delbtn` in styles.css) delete button. Click/mousedown handling lives on the WHOLE `.dlbl.ov` span (day letter + arrow together), not just the arrow glyph — clicking the letter used to fall through to the row's own drag (grab-hand cursor, no menu). Getting the drag-cancel right took two tries: a `draggable="false"` on the arrow does NOT stop the ancestor row's `draggable="true"` from claiming the drag (the browser's drag-source search walks up past a `false` descendant to the nearest `true` one regardless) — the actual fix is in each row's own `ondragstart="..."` string (and `dStart()` for `tRow`): check `event.target.closest('.dlbl.ov')` and `preventDefault()` to cancel the drag outright, letting the click fire normally. `draggable="false"` is kept as a harmless secondary signal but isn't what makes it work — if a similar "small control inside a draggable row" problem comes up elsewhere, go straight to the ondragstart-cancel approach. Non-recurring types (`_taskMoveToToday`/`_shopMoveToToday`/`_pupMoveToToday`/`_vidMoveToToday`) move that one item directly, no menu. Recurring/WR route through `_ovRowMoveClick`: same-week moves directly, past-week opens the same 4-option prompt as the bulk queue above — both call the shared `_wrScopePrompt(e,name,wkKey,onSkip,onThisTime,onSameDay,onChangeDay)` (overview.js) so wording/order can't drift between the two entry points. Title reads `"{name} (recurring) due last week"` (or `"due N weeks ago"` — `_weeksAgoLabel`, accurate for non-WR items which can be up to 4 weeks overdue, unlike WR week-misses which are always exactly 1). Options display top-to-bottom as **Skip past week / This time only / Same day / Change day to today** — `#wrScopePicker`'s markup renders skip-slot first/remove-slot second/this-slot third/all-slot fourth, so `_wrScopePrompt` deliberately maps skip→skipLabel, this-time→removeLabel, same-day→thisLabel, change-day→allLabel to get that order; don't "simplify" that mapping. "Skip past week" dismisses the miss without moving/completing anything (`_recSkipPastWeek` for non-WR — deliberately NOT `skipRecVirtThisWk`, whose linked-block cleanup filters by the *currently viewed* `wkOff` rather than the target past week; `writeWrOverride(...,{override_type:'skip'})` for WR, same as the Weekly Reset container's own top-block Move menu). "Same day" re-anchors the schedule to resume now without changing which weekday it falls on (`_recMoveAllFuture(...,keepDay=true)` / `wrMoveToThisWeek(...,allFuture,setDow=false)`); "change day" also changes the weekday to match today (`_nthWeekdayOfMonth` recomputes monthly nth-weekday rules). This arrow/menu is Today-list-only — the Weekly Reset container's own red overdue rows deliberately have no move action (see `rules/wr-system.md`).
- **Undo/redo**: every move above is a normal `pushUndo` closure mutating `st.wrRules`/`st.recurring`/`st.tasks`/`st.shopping`/`st.pupSessions`/`_vidDayMap`. Redo is generic (core.js `_stateSnap`/`_stateRestore` — a full pre-undo snapshot restored wholesale, not a per-action redo function), so any correctly-written undo closure gets redo for free as long as it only touches fields `_stateSnap` tracks. `_vidDayMap` (localStorage, used by video due-dates) is one of those tracked fields, same as `_vidStepDayMap` — don't add a new localStorage-backed field without also adding it to `_stateSnap`/`_stateRestore`, or redo will silently no-op for it.

## Sort Order

Three sort functions (`sortByTypeOrder`, `sortTasksForDay`, `sortByTBWeek`) all use the same tier system. As of 2026-08-20, manual day order can override important/timeblock-position — it used to be a bottom-tier tie-break only (deliberate widening, AskUserQuestion). As of 2026-08-21, **done was pulled back out into its own hard tier**: the 08-20 widening let manual order override done too, which stranded checked-off tasks wherever they'd been dragged instead of sinking them to the bottom — that was a correction, not a further widening. Don't re-narrow either change without checking with the user first.

**Hard tiers (checked first, in order — a manual reorder can NEVER move an item across these, or past an item in a different one):**
1. Travel (undone) — floats up, above birthday/holiday (so a same-day travel bar isn't cut off)
2. Birthday / Holiday — always
3. Overdue (undone) — floats up. Must stay pinned to the top until moved to today or completed; once it's neither, it drops into the manually-orderable pool below like anything else.
4. Done — always sinks to the bottom, even below a manually-placed undone item. (A done travel/birthday/holiday/overdue item isn't pinned by tiers 1-3 — those all require `!done` — so it already falls through to this tier.)

**Manual day order, else the old tier stack** (`_manualTieBreak(a,b,ds,naturalFn)`, overview.js): once both items agree on all four hard tiers above, if the day has a saved manual order (`_dayOrder()[ds]`, localStorage, drag/keyboard-reordered — see below) and BOTH items being compared are in it, their index there wins outright — this is what lets a manually-reordered selection move as a whole (it also implicitly overrides timeblock-position, since that check lives inside `naturalFn`, below manual order). `naturalFn` is the fallback used when one or both items have never been manually placed, so a freshly-added task still lands somewhere sensible instead of a random spot: important/fin-cancel(undone, floats up) → [`sortTasksForDay`/`sortByTBWeek` only: timeblock start-minute, blocked above unblocked] → `taskTypePri` category order → name. `_hardTierNatural(a,b)` (overview.js) is that fallback minus the timeblock step; `sortTasksForDay` wraps it with the timeblock check inline since only it has block data.

`taskTypePri` category order: birthday/holiday(1) → home(2) → my work(3) → work(4) → social/other(5) → vid(5.5) → vidstep(5.6) → non-WR recurring(6) → fin-cancel(6.5) → shopping(7) → pup(8) → weekly reset(9)

`sortByTBWeek` doesn't pass `ds` (only feeds `renderWkSummary`'s weekly-progress metric, not a rendered day column) so it always falls back to the same four hard tiers inlined directly (no `_manualTieBreak`/`_hardTierNatural` call — manual order is Today-list/weekly-cal-day-column only). Its tier order was out of sync with the other two (birthday before travel, done before overdue) until 2026-08-21 — corrected to match: travel > birthday/holiday > overdue > done > important > timeblock > taskTypePri.

Mobile `_mTaskTypePri` and `mSortToday` mirror the OLD stack exactly (manual-order-overrides-tiers not yet ported to mobile).

**Manual day-order drag/keyboard-reorder** (`_dayOrder`/`_dayOrderSet`, overview.js): reordering within the SAME day only ever touches this — it can't move an item across the travel/birthday/holiday/overdue hard tiers above (see previous paragraph for what it *can* now do). Wired independently in several places, all writing/reading the same `_dayOrder` map so they stay in sync:
- **Today list drag** (`_todDragRowId`, core.js): a delegated `dragstart`/`dragend`/`dragover`/`dragleave` set on `#todList` (set up once in `renderToday`, guarded by `_todListEl._reorderSetup`) tracks `_todDragRowId` = the dragged row's own `.id` whenever the drag source is a row already inside `#todList`, and live-inserts a `.tod-list-ph` divider at the cursor's insertion point during `dragover`. `dropOnTodayList` checks `_todDragRowId` FIRST — if set, `_dropReorderToday` builds the new order from the placeholder's position and returns early, leaving the rest of the function (cross-day/other-type drops) untouched. The container's own `drop-here` dashed-box highlight (inline `ondragover=` in index.html, meant for the cross-day-drop case) is suppressed during a reorder (`if(!_todDragRowId)this.classList.add('drop-here')`) — the placeholder divider is the only feedback wanted while reordering. No-op guard: captures the pre-drag row order and compares to the computed new order before writing/pushUndo — dropping back where it started does nothing (no stray undo toast).
- **Weekly cal day columns drag** (`_wkcDragTid`/`_wkcDragSrcDs`, core.js): same idea, but set/cleared directly inside each chip's own `dragstart`/`dragend` (in the per-chip loop in `renderWkCal`) — NOT via a delegated `#wkcCols` listener. A delegated listener was tried first and silently never fired: the chip's `dragstart` handler calls `e2.stopPropagation()` (to keep it from also triggering the column's own drag handling), which blocks the event from ever bubbling to a container-level listener. Each column's own `dragover`/`drop` handlers check `_wkcDragTid&&_wkcDragSrcDs===ds` first (placeholder = `.wkc-col-ph`) and return early on a match, before any of the existing cross-day-drop branches or edge-zone/travel-drag-select logic runs. Same no-op guard as the Today list. If any other same-column-reorder tracking is ever added elsewhere, remember delegation won't work here — hook the individual element's own handler instead.
- **Today-list keyboard nav** (`_todListKeyNav`, overview.js): Arrow selects/navigates, Shift+Arrow extends the selection, Cmd+Arrow reorders the selected block (multi-select aware, splice-based, same pattern as shopping), Delete/Backspace deletes. Adapted for the Today list's *mixed* item types (task/shop/wrrule/rec/pup/vid all in one list): delete dispatches per-type by id prefix — recurring/WR selections are handed off to the existing `_wrBulkDelete` (already single-undo for those two types); everything else (tasks/shopping/pup/video, video "delete" = unassign from today like its own X button) shares one combined undo built here in `_todListBulkDelete`. Vidstep/travel/birthday/holiday selections are silently skipped by the dispatcher (not deleted) — no keyboard-delete path for those yet.
- **Weekly-cal keyboard nav** (`_wkcColKeyNav`, overview.js, added 2026-08-20): same system as `_todListKeyNav` (Arrow select/extend, Cmd+Arrow reorder, Delete via `_todListBulkDelete` reused as-is — it's id-format-generic, not container-specific), scoped to whichever day column the last click actually landed in (tracked via `_lastSelWkcDs`, only ever set on click or by `_wkcAdvanceDay`'s own keyboard-driven day-cross — see below). **Drag-to-another-day-column within the same week** (the `col.addEventListener('drop', ...)` handler, overview.js ~line 1444) didn't update `_lastSelWkcDs` at all (2026-08-23 fix): selection correctly survives the move (nothing clears `selectedTasks`), but `_wkcColKeyNav` kept resolving the column from the stale SOURCE day, found no matching chips there post-move, and silently no-op'd Up/Down. Fixed by setting `_lastSelSurface='wkcCol';_lastSelWkcDs=ds;` right after `if(!dragId)return;`, before the per-drag-type dispatch, so it covers every draggable type uniformly. The cross-WEEK edge-drop (`setupWkcEdgeDrop`/`setupEdge`) does NOT need this: since 2026-08-22 it no longer navigates the view to the destination week, so the moved item's day column isn't rendered at all post-move — Up/Down correctly finding nothing there is expected, not a bug.
- **Plain Left/Right on overview with a selection = move ±1 day** (features.js, global keydown handler ~line 6300-6434, distinct from the drag-drop path above): when nothing's selected, Left/Right just shifts the viewed day (`shiftDay`); with a selection, it shifts every selected item's own date ±1 day instead (tasks/rec/wrec/WR-rule/shopping/video/timeblock/vidstep, one `undos` entry each, single combined `pushUndo`). Had the exact same `_lastSelWkcDs`-goes-stale bug as the drag path (2026-08-24 fix): now shifts `_lastSelWkcDs` by the same `dir` right after the move (and back by `-dir` inside the undo closure, using the block's own local `_shiftDs` helper) whenever the selection came from `_lastSelSurface==='wkcCol'`, so Up/Down works immediately after, and still works correctly post-undo.
- **Cross-day/cross-week arrow nav** (added 2026-08-20): in both the Today list and weekly-cal columns, hitting the top/bottom edge with a plain Arrow (no Shift/Cmd) advances into the prev/next day instead of stopping dead. `_todAdvanceDay(dir)` calls `shiftDay(dir)` (which already handles week-crossing) in a loop, skipping empty days, capped at 60 tries. `_wkcAdvanceDay(dir,ds)` does the date math itself and calls `shiftWk` when it crosses a week boundary, same empty-day-skipping/60-try cap. Both land the selection on the first/last item of whatever non-empty day they find.
- **Reset sort** (`_resetDayOrder(ds)`, overview.js, added 2026-08-20): clears `_dayOrder()[ds]` for one day, `pushUndo`-wrapped (undo/redo both work via the normal `_dayOrder`-in-`_stateSnap` mechanism, no special-casing needed). Button only renders when that day actually has a manual order (`(_dayOrder()[ds]||[]).length`) — deliberately NOT shown on weekly-cal day headers (tried, reverted per explicit request — "too visible" there). Lives in two places, both icon-matched to their row's sibling buttons: the collapsed/list-only Today-list bottom bar (`.tod-bottom-controls`, between Videos and Timeblock, full `<svg>`+label like its siblings — a bare glyph read as too-small next to their 11×11 icons) and the expanded-timeblock `#tbSum` bar (left of Auto, bare icon only, sized via the shared `_tbBtnSt` inline-style string so ✕/reset/Auto/Videos can never drift out of sync with each other again).
- **Scroll-follow on Cmd+Arrow reorder** (shopping list + Today list, added 2026-08-20): the moved item scrolls into view if it goes off-screen, via `_shopScrollTo(container,el)` — that helper only moves `scrollTop` if the element is actually outside the container's visible bounds, so it doesn't reintroduce the earlier "jumps the viewport every keypress" problem for moves that stay in view.

- **Drag-to-edge (prev/next week)** (`setupWkcEdgeDrop`/`setupEdge`, overview.js): dropping a task/rec/wrec/shop/video/vidstep/travel/goal chip on the `.wkc-edge-l`/`.wkc-edge-r` zones flanking the week calendar moves its date into the adjacent week WITHOUT navigating the view there (added 2026-08-22 — it used to call `shiftWk(dir)`, which both moved the item and jumped the displayed week to follow it; now each branch calls `save();renderAll()` (or the equivalent already-rendering helper like `_recMoveAllFuture`/`_vidAssignToDay`) directly instead, so the moved item just disappears from the still-current week, same as any other date edit). The Weekly-Goals-column horizontal chip drag (`onUp` closure, ~line 2052) follows the same rule via its own `renderWkCal();renderWkSummary()`. Don't reintroduce `shiftWk(dir)` in these paths.
- **Every drag-type dispatch must handle `shop::` alongside `wrec::`/`rec::`/`vid::`**: shopping items are their own array (`st.shopping`, not `st.tasks`), so a switch that's missing a `shop::` branch doesn't error — it silently falls through to the generic task-lookup at the bottom, finds nothing in `st.tasks`, and no-ops. `setupWkcEdgeDrop`/`setupEdge` (overview.js) were missing it entirely (2026-08-22 fix, ported the same `st.shopping`-lookup-plus-`_shopTopOrder`-reorder logic already used by `dropOnTodayList`/`dropOnWkcCol`) — every other multi-type drag dispatcher in the file already had it. If a new drag target is added anywhere, grep all four (`wrec::`/`rec::`/`shop::`/`vid::`) together to confirm the new function has all of them, not just the ones that happened to get copy-pasted in.

Both drag paths persist a **fresh full array** rebuilt from the current rendered order (not a delta), same "recompute the whole thing" pattern as the shopping list's Cmd+↑/↓. Because `sortTasksForDay` drives both the Today list AND the weekly cal's day columns (`renderWkCal` calls it directly per day), a reorder in either view shows up in the other automatically — no separate sync. `_dayOrder` is localStorage, not `st.*` — it's included in `_stateSnap`/`_stateRestore` (core.js) alongside `_vidDayMap`/`_vidStepDayMap` so redo covers it; don't forget that pairing if this ever moves to a DB column.

- **Multi-select drag-to-another-day undo must be ONE combined entry, not two** (overview.js day-column drop handler, 2026-08-25 fix): dragging a multi-selected group moves the dragged item via a helper (`_vidAssignToDay`/`_vidStepAssignToDay`) that pushes its OWN undo, then separately moves the other selected items via `_moveOtherSelected` (which collects undos into an array the caller pushes). If you naively let the helper's pushUndo stand and then push a SECOND pushUndo for the others, one Undo press only reverts the second entry, leaving the originally-dragged item still moved — "undo only reverts one at a time" was this. Fix pattern: snapshot `undoStack.length` before calling the helper, call it, then `const _selfUndo=(undoStack.length>_lenBefore)?undoStack.pop():null` to reclaim its undo closure (safe — only pops if the helper actually pushed one; it can no-op via an early-return guard like "already on this day"), then build ONE `pushUndo` that runs `_selfUndo.fn()` plus the other items' undos together. `rec::`/`pupsess::`/`shop::` branches in this same handler already did it right (undo built inline, no separate helper call) — only `vid::`/`vidstep::` needed this pop-and-merge trick because they route through a self-contained helper.

**`_lastSelSurface`/`_lastSelWkcDs`** (features.js/overview.js, added 2026-08-20): which list a keystroke belongs to can't be determined from "does a matching row/chip id exist in container X" — it's often true in more than one place at once: `#shopOv` shows every undone shopping item (not date-filtered), so a shop item due today has an identical row id there AND in `#todList` simultaneously; a recurring task (daily cadence especially) renders the identical chip `data-tid` in every weekly-cal column it appears in. `_lastSelSurface` (`'todList'`/`'shopOv'`/`'wkcCol'`/`'vidOv'`) records which container a click actually happened in — set once per click in `selTask()` (features.js, via `e.currentTarget.closest('#todList,#shopOv,.wkc-col')`) and, separately, directly inside weekly-cal's own hand-rolled chip click handler (`renderWkCal`, overview.js) since that one doesn't call `selTask`, and inside `_vidOvClickSelect`/`_vidCalSelectChip` (overview.js, 2026-08-26) for the video popup's own list/calendar. `_lastSelWkcDs` additionally records WHICH day column, for the same reason — `_wkcColKeyNav` resolves its column from this tracked value, never by searching `#wkcCols` for a chip matching the selected id (that search silently redirected everything to the first/Monday match whenever a recurring task's duplicate tid was involved — "arrow nav gets stuck around recurring tasks"). Kept in sync by `_wkcAdvanceDay` when it crosses into a new column. `_shopOvKeyNav`/`_todListKeyNav`/`_wkcColKeyNav`/`_vidOvKeyNav` all gate on the surface flag FIRST, before touching `selectedTasks`/`_vidOvSelSet` at all — whichever list was last clicked owns the keystroke. `_vidOvKeyNav` was the odd one out until 2026-08-26 — it unconditionally hijacked plain Up/Down any time the video popup was open (`panel.style.display==='block'`) regardless of `_lastSelSurface`, so pressing Up/Down after clicking a weekly-view task while the popup sat open beside it silently moved the popup's own selection instead. Fixed the same way as the others: bails (`return false`) on plain Up/Down unless `_lastSelSurface==='vidOv'`. Note the video popup's reverse cross-view sync (`_vidOvSyncFromGlobalSel`, see pages.md "Overview video panel selection echoes...") can still update the popup's OWN highlighted row as a side effect of a weekly-view click — that's intentional (the popup echoes whatever video task got selected elsewhere) and does NOT flip `_lastSelSurface` back to `'vidOv'`, so Up/Down still correctly continues to control the surface that was actually clicked.

**No-op drag guard**: any drag-reorder handler that persists a new order and fires `pushUndo` must first compare the computed new order to the pre-drag order and bail out if they're identical — otherwise dropping an item back exactly where it started still fires an undo toast for nothing. Sites using this pattern: Today-list/weekly-cal manual reorder (above), the standalone Shopping List page's manual-mode drag (`renderShopFull`, features.js — this one also gained `pushUndo` entirely; it had none before and reorders were silently non-undoable), Ideas drag reorder (`_ideaSetupDrag`, features.js — same, gained `pushUndo`), and the video overview panel's child-video/B-video drop-line reorder (`_vidOvContentDrop`, overview.js). Copy this pattern for any new drag-reorder feature.

## Task Modals
- **`#tModal`**: add (`openTModal(cat='')`) + edit (`openEditTask(id)`). Save: `saveTModal()`.
- **`#qaPopup`** (`openQA(ctx,btn,ds,kcat)`): cat defaults `kcat` when `ctx==='kanban'` OR `ctx==='wkc'` and `kcat` provided, else `'Home'`.
- **`#qaPopup` centering, no-anchor case** (2026-08-24/25 fix): centers over `#main` (measuring its own rendered size, then writing rounded whole-pixel `top`/`left`), NOT `top:50%;left:50%;transform:translate(-50%,-50%)`. That older pattern has two bugs on any popup whose height isn't a whole number of pixels (i.e. always): (1) `-50%` of a fractional height lands the translate on a fractional pixel, and GPU-compositing an element at a fractional offset visibly blurs its own contents, not just its edges; (2) the `fadeUp` open animation also animates `transform`, so it was fighting the same property used for centering, causing a jump on open. Measuring post-layout and writing plain `top`/`left` leaves `transform` free for the animation and removes the fractional pixel. If any other popup gets this same "blurry/glitches on open" complaint, check for this exact pattern first.

## Chip & UI Notes
- **Hover-X**: `.chip-del` last flex child. X removes from ALL views + linked blocks. Exception: X on TB block itself → `delBlock` only.

- **Checkbox rendering** (rewritten 2026-08-25 — the previous entry here was backwards and actively caused the bug it claimed to prevent): All unchecked checkboxes (`.chk`, `.tb-chk`, `.chip .wchk`) render their ring via a `background-image` data-URI SVG circle (`background-color` for the fill, `border-radius:50%` kept only to clip that fill/image to a circle — no actual CSS `border` on the ring anymore). Root cause history: `.chk`/`.chk-wrap` used to carry `transform:translateZ(0)` "for GPU compositing to prevent oval distortion" — backwards. Forcing GPU-layer promotion on a circle whose row sits at an arbitrary fractional-pixel Y (unavoidable with variable-height rows) made the CSS `border`'s per-edge anti-aliasing round unevenly (thicker top on one row, thicker bottom on another) — that transform was *causing* the oval look, not preventing it. Removing it helped but didn't fully fix it, because a plain CSS `border` is inherently subject to this at any fractional Y, transform or not. Checked-state ring (`:checked::after`, still `box-shadow:inset 0 0 0 1px`) wasn't touched — its ring color barely contrasts its own fill, so the artifact was never visible there; if it ever is, apply the same SVG treatment. Don't reintroduce `transform:translateZ(0)`/`will-change:transform` on any of these — that's what started this.
- **Checkbox/`.tn` optical alignment gotcha** (2026-08-20): flexbox `align-items:center` centers the checkbox and `.tn` text's *bounding boxes* perfectly (confirmed via `getBoundingClientRect` — identical center Y), but that's not the same as looking centered — DM Sans (like most fonts) reserves more space above cap-height than below the baseline, so text without descenders (g/y/p/j — "Journal" was the reported case) visibly sits higher than a true circle centered the same way. `line-height:1` alone does NOT fix this (line-height adds/removes leading symmetrically; it doesn't touch the font's own ascent/descent asymmetry) — needs an actual `transform:translateY()` nudge on top of it. **This fix must stay scoped to the exact context it was calibrated for, never applied to the base `.tn` class** — Weekly Reset and Shopping rows were already correctly aligned at their smaller size, and applying the same nudge there broke them (confirmed live by stripping it and watching them snap back). - **Vidstep TB copy/paste (Build/VO/Cut ONLY)**: Cmd+C on a vidstep TB block (detected via `vidstep-` selection ID when TB is open) copies to `_copiedBlocks` with `_vidStepVid` + `_vidStepName`. - **Vidstep per-day independence**: `seen` sets in `_vidStepTasksForDayWithOverdue` and `_vidStepOvCount` use `vidId::step::day` keys (not `vidId::step`), so the same step on different days produces separate entries. IDs include day suffix: `vidstep-{vid}-{step}-{day}`. **Regex matching MUST try date-suffixed pattern first**: `sid.match(/^vidstep-(.+)-(step_\w+)-\d{4}-\d{2}-\d{2}$/)||sid.match(/^vidstep-(.+)-(step_\w+)$/)` — plain `$` anchor alone will never match IDs with the day suffix.

- **Vidstep done consistency (CRITICAL)**: ALL overdue vidstep checks MUST use `_vidStepComputeDone()` — never rely on `val.done` alone. `val.done` only covers Th/Des (daymap flag). No-day-scope toggles also write `doneDays` for block-less days so instance rows stay consistent.
- **Vidstep instance moves (CRITICAL)**: NEVER write `m[key]={ds,...}` wholesale (drops `extraDays`/`doneDays`) and NEVER unconditionally set `m[key].ds` for a dragged instance. Daymap undo snapshots must be deep copies (`JSON.parse(JSON.stringify())` — entries hold nested arrays/objects).
- **Vidstep overdue counting/rollover**: banner + rollover scan daymap primaries AND `extraDays` AND orphaned past blocks, deduped with per-day keys (`vidId::step::day`), matching `_vidStepTasksForDayWithOverdue`. Rollover moves overdue extraDay instances to today (merging if today already has the step).
- **Vidstep reconstruction**: `_vidStepReconstructBlocks()` — fixes vidstep blocks with `sm < HOURS[0]*60` by reassigning to 8am default (NEVER delete — blocks with `sm=0` from null `start_minutes` must be preserved). For multi-day Build/VO/Cut, only creates daymap entry if none exists (does NOT overwrite existing to today, preserving overdue). For single-day Th/Des, always syncs daymap to today.
- **Vidstep operations — today list vs weekly chips**:
  - **Today list** (`tRowVidStepVirt`): Each instance scoped to `_vidStepDay`. Drag uses `vidstep::vid::step::day`. Toggle passes `forDay` to `_vidStepToggleDone`. `_hasTBToday` checks blocks on `_todDs` (today's date) only — NOT `_vidStepDay`. This ensures overdue vidsteps from past days correctly show as "not on TB" if there's no block on today.
  - **Weekly chips**: check/delete pass `forDay=t.due_date` → only affect that day's blocks. Drag uses `vidstep::vid::step::sourceDay` — drop moves source day's blocks and updates only the dragged instance in the daymap (primary if `ds===sourceDay`, else extraDay swap; doneDays carried). Dropping a calendar-only instance on the TB grid creates a block at the drop position.
  - `_vidStepToggleDone(vidId,step,checked,_fromTB,forDay)` — `forDay` scopes to that day's blocks; omit for all blocks. Pushes undo (except when `_fromTB`=true — TB handler pushes its own). Auto-creates daymap entry if blocks exist without one.
  - `_vidStepUnassign(vidId,step,forDay)` — `forDay` removes only that day's blocks and reassigns daymap to another day if needed; omit to remove everything.
- **Vidstep done computation**: `_vidStepComputeDone(vidId,step,ds,mapEntry)` — for Build/VO/Cut, checks blocks on that specific day only (no cross-day fallback). For Th/Des, uses daymap done flag.
- **Vidstep default durations**: Build/VO/Cut → 60 min, Th/Des → 30 min (unless manually changed).
- **Vidstep cross-view sync**: toggling a stage anywhere (videos page dot via `cycleVidStep`, overview stage square, overview checkbox, video edit modal) must sync all three: `v[step]`, `_vidStepDayMap[key].done`, and timeblock block `_done`. Sync code in `cycleVidStep`, `_vidOvToggleStep`, stage square click handler, and modal save path.
- **Vidstep uncheck preserves past blocks (Build/VO/Cut)**: When a stage is unchecked (set to `not_started`), only blocks on today or future days (`bl.ds >= todayDs`) are unchecked. Past completed blocks stay done — they represent work already finished. Checking a stage done still marks ALL blocks done. Undo restores exact previous per-block states. Applies to: `_vidOvToggleStep`, stage square click handler, and their undo paths.
- **Vidstep copy/paste**: Cmd+C copies vidstep tasks (`_isVidStep` flag, regex `^vidstep-(\d+)-(step_\w+)` handles both ID formats). Cmd+V on Build/VO/Cut calls `_vidStepAssignExtraDay` — adds day to calendar WITHOUT creating a TB block. Th/Des steps can't be pasted (toast warning). Target day from `_pasteColDates` (weekly column click).
- **Vidstep DB persistence**: `_vidStepVid` stored in `vid_id` column, `_vidStepName` in `rec_id` column. On load, blocks with `vid_id` + `rec_id` starting with `step_` are recognized as vidstep blocks. `_vidStepReconstructBlocks()` tags legacy blocks (title matching) and ensures daymap entries exist. Must run before sort and before `_hasTBToday`.
- **Vidstep timeblock moves**: use `sbUpdateBlock(id, {day_date: ds})` — NOT `{ds}`. The DB column is `day_date`.
- **Vidstep sorting**: `sortTasksForDay` → `tbSm()` has explicit `_type==='vidstep'` check before the `_vidId` check (vidstep blocks use `_vidStepVid`, not `_vidId`).
- **Vidstep focus**: `_renderVidOvMenu` focus mode checks `_vidStepDayMap` entries in addition to `_vidDayMap` and `post_date`.
- **Vidstep TB drop (Build/VO/Cut)**: When dragged from weekly chip with source day, moves source day's blocks to TB day. When dragged from today list or vid overview panel (no source day), adds new block via `_vidStepAddBlock`. TB undo only removes the added block (does NOT call `_vidStepUnassign`).
- **'A' key + vidstep**: Skips if a block already exists on that day for the step. Otherwise calls `_vidStepAddBlock`.
- **TB block dedup**: When moving tasks between days in weekly cal, auto-create of TB block on target day is skipped if a block for that task already exists on the target day. Prevents duplicate blocks from same-day drops or re-drops.
